## 1. The story: a filing cabinet of folders

Picture the back office of a small shop. There's a **filing cabinet**. Each drawer is labelled ("Products", "Orders", "Customers"). Inside each drawer are **folders**, one per product or order.

Open one product folder and **everything about that product is inside**: the name, the price, a list of sizes, a sheet with the supplier's details. You don't need to run to another drawer to understand the product.

```text
┌────────────── Cabinet: "shop" ────────────────┐
│ ┌─ Drawer: products ─┐ ┌─ Drawer: orders ───┐ │
│ │ ▣ folder: Mug      │ │ ▣ folder: #1001    │ │
│ │ ▣ folder: T-shirt  │ │ ▣ folder: #1002    │ │
│ │ ▣ folder: Lamp     │ │ ▣ folder: #1003    │ │
│ └────────────────────┘ └────────────────────┘ │
└───────────────────────────────────────────────┘
```

Map it to MongoDB:

| Filing cabinet | MongoDB | SQL equivalent (roughly) |
|---|---|---|
| The cabinet | **Database** | Database / schema |
| A drawer | **Collection** | Table |
| A folder | **Document** | Row (plus its child rows) |
| A label on a sheet | **Field** | Column |
| The folder number | **`_id`** | Primary key |

The big difference from SQL: a folder can hold **nested sheets and lists**. A SQL row is flat; a document can contain arrays and sub-documents.

> **Remember:** a document is a self-contained folder. Everything you usually need about one "thing" can live inside it.

## 2. Why the document model exists

In a relational database, one product with 3 sizes and 2 images is typically spread over 3 tables and needs joins to rebuild. Your Node.js code then turns those rows back into one object.

MongoDB stores the object **in the shape your code already uses**:

- **Fewer joins:** one read returns the whole product.
- **Natural mapping:** a document looks like the JS object you send as JSON to React.
- **Flexible evolution:** add a field to new documents without a migration that locks a huge table.

The trade-off: you must design documents around **how you read the data** (see [Schema design](/lessons/mongodb-schema-design)). For a broader comparison, read [SQL vs NoSQL](/lessons/sql-vs-nosql).

## 3. JSON vs BSON

You write JSON-like objects in mongosh and in Mongoose. But MongoDB never stores text JSON. It stores **BSON** (Binary JSON).

| | JSON | BSON |
|---|---|---|
| Format | Text | Binary |
| Types | string, number, boolean, null, array, object | All of those **plus** ObjectId, Date, Int32, Int64, Double, Decimal128, binary data… |
| Numbers | One "number" type | Distinct integer, double and decimal types |
| Traversal | Must parse the whole text | Each element stores its **type and length**, so the server can skip over fields it doesn't need |
| Size | Often smaller for tiny docs | Slightly bigger (length prefixes), but much faster to scan |

Why this matters:

1. **Typed:** `19.99` stored as a Double is different from `Decimal128("19.99")`. A query for a String `"5"` won't match the number `5`.
2. **Traversable:** because every element carries its length, the server can jump straight to `price` without parsing `description`.
3. **Richer:** JSON has no date type. BSON does.

> **Remember:** JSON is what you type; BSON is what MongoDB stores. BSON is binary, typed and length-prefixed so it is fast to scan.

## 4. The BSON types you must know

### ObjectId: the default `_id`

An **ObjectId** is a 12-byte value, usually generated by the **driver** (in your Node app) before the insert reaches the server:

```text
┌──────────────┬──────────────────┬────────────┐
│  4 bytes     │  5 bytes         │  3 bytes   │
│  timestamp   │  random value    │  counter   │
│  (seconds)   │  (per process)   │  (+1 each) │
└──────────────┴──────────────────┴────────────┘
   6acb4626      a672d45373          fdcb35
```

- **Timestamp:** seconds since the Unix epoch, so you can read the creation time back.
- **Random value:** generated once per process, so two app servers don't collide.
- **Counter:** starts at a random value and increments, so one process can create many IDs per second.

```js
const id = new ObjectId()
id.getTimestamp() // ISODate('2026-10-11T08:17:42.000Z')
```

Because the timestamp comes first, ObjectIds are **roughly time-ordered**: sorting by `_id` approximates insertion order. It is only *roughly* ordered: IDs from different machines in the same second, or from machines with skewed clocks, can interleave.

⚠️ This is also why an ObjectId is a bad **ranged** shard key: every new value is larger than the last, so all inserts hit one shard (see [Sharding](/lessons/sharding)).

### Numbers: Int32, Int64, Double, Decimal128

| Type | Use it for | mongosh |
|---|---|---|
| **Int32** | Small counts, quantities | `NumberInt(3)` (or a plain integer literal like `3`) |
| **Int64** | Big counters, IDs, millisecond values | `NumberLong("9007199254740993")` |
| **Double** | Measurements, ratings, scientific values | `4.5` |
| **Decimal128** | **Money** and anything needing exact decimals | `NumberDecimal("19.99")` |

Why not store money as a Double? Because binary floating point can't represent most decimal fractions exactly:

```js
0.1 + 0.2 // 0.30000000000000004
```

Sum a million order lines like that and your revenue report is off by cents. **Decimal128** stores up to 34 exact decimal digits. (The other common fix is storing integer **cents** as Int64.)

⚠️ Pass Int64 and Decimal128 values as **strings**: `NumberLong(9007199254740993)` goes through a JS number first and loses precision.

### The rest

- **String:** UTF-8 text.
- **Date:** a 64-bit integer of **milliseconds since the Unix epoch, in UTC**. Store real dates, never strings like `"11/10/2026"`, or range queries and sorting break.
- **Boolean:** `true` / `false`.
- **Array:** an ordered list; elements can be any type, including documents.
- **Embedded document:** a document inside a field (`address: { city: "Pune" }`).
- **Null:** an explicit "no value". Note that `{ field: null }` in a query matches documents where the field is null **or missing**.

> **Remember:** use Date for dates and Decimal128 (or integer cents) for money. Types are part of your data, not a detail.

## 5. The `_id` field rules

Every document has an `_id`, and it follows four rules:

1. **Required:** if you don't provide one, it's generated (an ObjectId) for you.
2. **Unique** within the collection: there's always a unique index on `_id`, and you can't drop it.
3. **Immutable:** once inserted, it can't be changed.
4. **Any type except an array** (regex and undefined aren't allowed either). Strings, numbers and compound documents are all fine.

```js
db.products.updateOne({ sku: "MUG-01" }, { $set: { _id: 5 } })
// MongoServerError: Performing an update on the path '_id'
// would modify the immutable field '_id'
```

To "change" an `_id`, you insert a new document and delete the old one.

## 6. A real example: an e-commerce product

```js
db.products.insertOne({
  // _id is generated: ObjectId('...')
  sku: "TSHIRT-BLU-01",
  name: "Classic Cotton T-Shirt",
  price: NumberDecimal("19.99"),          // exact money
  currency: "INR",
  stock: 120,                              // Int32
  isActive: true,
  tags: ["clothing", "cotton", "summer"],  // array of strings
  sizes: [                                 // array of documents
    { size: "M", stock: 50 },
    { size: "L", stock: 70 }
  ],
  supplier: {                              // embedded document
    name: "Acme Textiles",
    country: "IN"
  },
  discontinuedAt: null,
  createdAt: new Date()                    // BSON Date (UTC)
})
```

One read returns the full product page: sizes, tags and supplier included.

## 7. Limits you must design around

- **16 MB per document** (BSON size). It's a guard rail, not a target. A document that grows forever (all reviews of a product, every event of a user) will eventually hit it. For large files, use **GridFS**, which splits a file into chunks.
- **Nesting depth:** MongoDB officially supports up to **100 levels** of nested documents. If you're anywhere near that, the model is wrong.
- Big documents also cost you before they hit the limit: every read pulls the whole document into memory, even if you only display one field.

> **Remember:** 16 MB is the hard ceiling, but the real problem starts much earlier. Unbounded arrays are the usual culprit.

## 8. Flexible schema, not "no schema"

MongoDB doesn't force every document in a collection to have the same fields. That's great for:

- Products with different attributes (a laptop has `ram`, a shirt has `size`).
- Rolling out a new field without downtime.

But your **application** always has a schema: your code expects `price` to exist and to be a number. Without discipline, you end up with `price`, `Price` and `price: "19.99"` (a string) in the same collection, and queries silently miss documents.

### Schema validation with `$jsonSchema`

You can make the server reject bad documents:

```js
db.createCollection("products", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["sku", "name", "price"],
      properties: {
        sku:   { bsonType: "string" },
        name:  { bsonType: "string", minLength: 1 },
        price: { bsonType: "decimal", minimum: 0 },
        tags:  { bsonType: "array", items: { bsonType: "string" } }
      }
    }
  },
  validationLevel: "strict",  // which documents are checked
  validationAction: "error"   // what happens on failure
})

db.products.insertOne({ sku: "MUG-01", name: "Mug", price: 10 })
// MongoServerError: Document failed validation
// (errInfo says price: "type did not match", consideredType: 'int')
```

| Option | Values | Meaning |
|---|---|---|
| `validationLevel` | `strict` (default) | Check **all** inserts and updates |
| | `moderate` | Check inserts, and updates to documents that are **already valid**; old invalid documents can still be updated |
| | `off` | No validation |
| `validationAction` | `error` (default) | Reject the write |
| | `warn` | Allow the write, but log a warning |

Add a validator to an existing collection with `collMod`. Existing documents are **not** re-checked when you add it; only future writes are.

```js
db.runCommand({ collMod: "products", validator: { $jsonSchema: { /* ... */ } },
                validationLevel: "moderate" })
```

A practical rollout: start with `warn` (or `moderate`) on a live collection, fix the data the logs reveal, then switch to `strict` + `error`.

> **Remember:** flexible schema means the database *can* store different shapes, not that it *should*. Enforce structure with Mongoose and/or `$jsonSchema`.

## 9. Common mistakes

- ❌ **Money as Double** → rounding errors in totals. Use Decimal128 or integer cents.
- ❌ **Dates as strings** → `"2026-9-1" > "2026-10-1"` as strings, so sorting and ranges break.
- ❌ **Mixed types in one field** (`"5"` and `5`) → `find({ qty: 5 })` misses half the data.
- ❌ **Assuming `_id` order is exact insertion order** → it's only roughly time-ordered. Use a `createdAt` field when order matters.
- ❌ **Relying only on Mongoose for validation** → scripts, other services and the shell bypass it. Server-side `$jsonSchema` catches everything.
- ❌ **Growing arrays forever** inside one document → slow reads, then the 16 MB wall.

## 10. Don't confuse these

| | Document (MongoDB) | Row (SQL) |
|---|---|---|
| Shape | Nested: arrays, sub-documents | Flat columns |
| Schema | Flexible per document (optionally validated) | Fixed per table (`ALTER TABLE` to change) |
| Related data | Often embedded in the same document | Usually in other tables, joined |
| Identity | `_id` (ObjectId by default) | Primary key (often auto-increment) |
| Max size | 16 MB | Depends on the engine and column types |

## 11. When the document model is a poor fit

- Data that is **highly relational** and queried in many unpredictable ways (heavy ad-hoc reporting across many entities) is often simpler in SQL.
- Data where the **same fact is shared and updated constantly** by many records (embedding copies would mean updating thousands of documents).
- Teams that won't enforce any schema discipline: the flexibility becomes a mess.

MongoDB handles relationships and multi-document [transactions](/lessons/mongodb-transactions) fine; the point is to pick the model whose **natural shape matches your access patterns**.
